# ZenxPOS legacy vulnerability register

This register records security weaknesses confirmed during the Laravel-to-Node.js migration. It is a static source review, not evidence that an attack or breach has occurred. The **Data Breach** column describes the information or capability that could be exposed if the issue were exploited.

Update this file whenever another legacy weakness is confirmed. Do not add speculative findings without source evidence. Resolution values mean:

- **Resolved:** implemented and covered by the Node test suite.
- **In progress:** replacement work has started but is not complete.
- **Planned:** confirmed issue whose owning migration stage has not been converted.

| Functionalities | Issue | How attackers attack | Example | Data Breach | New Code Resolution |
| --- | --- | --- | --- | --- | --- |
| Password reset — **Critical** | `resetPassword` accepts a mobile number and new password without requiring a verified OTP, reset token, or authenticated session. OTP verification is a separate request and `resetPassword` never checks `otp_status`. Evidence: `dev/app/Http/Controllers/Api/Login.php`, reset method around lines 362–427. | An attacker who knows a user's mobile number calls the reset endpoint directly and chooses a new password. | `POST /api/resetPassword` with `{"mobile":"9876543210","newPassword":"Owned1@","confirmPassword":"Owned1@"}` can bypass `/verifyOtp`. | Potential full account takeover, followed by access to the tenant's customers, sales, stock, billing, and configuration data. No breach is confirmed by this review. | **Resolved:** Node reset requires a verified, short-lived, one-time reset token bound to the mobile, user, and client. Consumption, bcrypt update, challenge deletion, and audit creation occur transactionally. Replay is tested and denied. |
| Forgot password and OTP — **High** | The OTP is stored as a plaintext integer, has no expiry, has no attempt counter, and is returned directly in the API response. Evidence: `Login.php` around lines 212–278 and `client_users.otp`. | Anyone who requests a reset receives the secret in the response. A previously issued OTP can also remain valid indefinitely and can be guessed repeatedly. | The legacy success response includes `{"data":{"otp":1234}}`; `/verifyOtp` accepts repeated four-digit guesses. | Potential account takeover. OTP values may also enter API logs or monitoring systems. No breach is confirmed. | **Resolved:** Node returns no OTP, stores only an HMAC challenge in Redis with native expiry when configured (database cache fallback otherwise), expires it after 10 minutes, limits verification to five attempts, enforces a resend cooldown, and sends through a configurable HTTPS delivery webhook. |
| Public authentication endpoints — **High** | No active rate-limiter configuration was found in `bootstrap/app.php` or a `RateLimiter` provider. The obsolete `app/Http/Kernel.php` mentions `throttle:api`, but the Laravel 12 bootstrap does not register that Kernel configuration. | Attackers automate login password guessing, mobile-number discovery, OTP requests, and OTP guesses from one or many IP addresses. | Thousands of `/api/login`, `/api/forgotPassword`, or `/api/verifyOtp` requests can be sent in a short period. | Potential account takeover, denial of service, SMS/email cost abuse, and user enumeration. | **In progress:** Node reset challenges enforce a database-backed per-mobile resend cooldown and attempt ceiling. Distributed per-IP and account login limiting is still required before public deployment. |
| Login error handling — **Medium** | Login returns different messages for an unknown email/mobile and an incorrect password. Evidence: `Login.php` around lines 65–94. | Attackers submit lists of email addresses or mobile numbers and classify accounts using the response text. | “Email or mobile is incorrect” confirms absence, while “Password is incorrect” confirms an existing account. | Exposure of the registered-user directory, enabling targeted phishing and credential stuffing. No breach is confirmed. | **Resolved:** Node login always returns `Invalid email/mobile or password.` and tests cover both cases. |
| Admin passwords — **Critical** | Admin passwords use unsalted MD5. New admins also receive the fixed default `123123`. Evidence: `admin/Login.php:43`, `admin/Password.php:47–48`, and `admin/Admins.php:114,194`. | An attacker who obtains the admin table cracks MD5 hashes rapidly with commodity hardware or rainbow tables. The attacker can also try the public default password. | `md5("123123")` is a known, reusable hash and requires no per-user salt. | Potential full platform-administrator takeover and exposure or modification of every tenant. No breach is confirmed. | **Planned for Stage 10:** migrate hashes to Argon2id or bcrypt, force resets for MD5/default-password accounts, reject known/default passwords, and use constant-time framework verification. |
| Client provisioning — **High** | Every newly created client administrator receives the same password `123123`. The model hashes it before storage, but the credential itself remains predictable. Evidence: `admin/Clients.php` around lines 369–385. | Attackers identify a new client or try the default across known mobile numbers and emails. | Log in as a recently provisioned store administrator using `123123`. | Potential takeover of newly provisioned tenant accounts and their POS data. No breach is confirmed. | **Planned:** generate a random one-time activation token, deliver it out of band, require a strong password at activation, and never create usable shared credentials. |
| API logging — **High** | `ApiLogger::error` records `$request->all()`, exception messages, local filenames, and full stack traces. Several info/warning calls also pass complete request bodies. Evidence: `dev/app/Http/Traits/ApiLogger.php:12–25` and controller calls containing `'input' => $request->all()`. | An attacker triggers errors after submitting passwords, OTPs, personal details, payment values, or crafted content. Anyone with log access can then retrieve those values. | A failed password-change or reset request can write password fields and OTP data to the API log alongside server paths. | Potential disclosure of credentials, OTPs, customer PII, financial data, tokens, internal paths, and implementation details. No breach is confirmed. | **Resolved for migrated routes:** the Node error handler emits a request ID and generic error without logging bodies, credentials, stack traces, or database errors. A structured allowlist/redaction logger will be required for later routes. |
| JWT tenant lifecycle — **High** | JWT middleware reloads only `client_users` and checks that user's `status/trash`. It does not reload the parent client account or validate the contract start/end dates on protected requests. Evidence: `dev/app/Http/Middleware/JwtMiddleware.php:19–30`. | A user keeps using an already-issued token after the tenant is disabled or its contract expires. | A token issued before `users.status` becomes `0` continues reaching protected POS APIs until token expiration/revocation. | Continued access to tenant operational and customer data after access should have ended. No breach is confirmed. | **Resolved:** every protected Node request reloads the user, role, client status, tenant identity, and contract dates. Cross-client claims and expired contracts are denied by tests. |
| JWT lifetime and revocation — **Medium** | The legacy default JWT lifetime is 10,080 minutes (7 days). Password changes do not explicitly invalidate already-issued JWTs. Evidence: `dev/config/jwt.php:104` and password-change logic. | A stolen token remains useful for days, including after the victim changes their password. | A token copied from browser storage can be replayed until its seven-day expiry. | Prolonged unauthorized access under the victim's account. No breach is confirmed. | **Resolved for migrated API:** default lifetime is 8 hours; issuer, audience, algorithm and expiry are enforced; tokens contain a password-hash version so a password change immediately invalidates older tokens. |
| JWT error responses — **Low** | The catch-all JWT middleware response includes the exception message, while logs include source file and line details. Evidence: `JwtMiddleware.php:45–55`. | Attackers submit malformed tokens and compare internal parsing errors to learn library behavior and configuration. | A malformed token receives `{"error":"Unauthorized","message":"<library detail>"}`. | Limited internal implementation disclosure that can help later attacks. No breach is confirmed. | **Resolved:** Node authentication returns only `Unauthorized.` and does not expose verification exceptions. |
| Admin authorization — **High** | Admin protection is implemented manually inside individual controller methods instead of route middleware. `/dashboard` and `/change_password` render without checking `adminId`. Evidence: `routes/web.php:19–24`, `admin/Login.php:58–60`, and `admin/Password.php:20–22`. | Attackers browse unguarded admin routes or find future controller actions where a developer forgot the repeated session check. | Directly request `{ADMIN_PATH}/dashboard` without an authenticated admin session. | Possible exposure of admin pages and a high risk of future unauthorized administrative actions. The reviewed dashboard route itself renders a view; no confirmed data extraction was established. | **Planned for Stage 10:** one mandatory admin authentication/authorization middleware will guard an admin route group; controllers will not implement optional manual checks. |
| Admin session lifecycle — **High** | Successful login stores identifiers without regenerating the session ID. Logout only removes two keys and does not invalidate the session or regenerate the CSRF token. Evidence: `admin/Login.php:49–53,62–67`. | An attacker fixes or steals a pre-authentication session ID, waits for the victim to log in, then reuses that session. A residual session can also survive incomplete logout handling. | Victim authenticates using a session ID previously supplied or captured by the attacker. | Potential administrator session hijacking and cross-tenant administrative access. No breach is confirmed. | **Planned for Stage 10:** regenerate the session on login and privilege change; invalidate the whole session and regenerate the CSRF token on logout; use secure, HTTP-only, same-site cookies. |
| Administrative delete actions — **High** | Destructive actions are exposed as `GET` routes, including deletion of clients, admins, business types, features, bill formats, and other settings. Evidence: `dev/routes/web.php` delete routes around lines 32–119. | A malicious site, link, crawler, prefetcher, or compromised page causes an authenticated admin's browser to navigate to a deletion URL. GET requests are not protected as state-changing CSRF operations. | An admin clicks a link to `{ADMIN_PATH}/delete/client/42`, or a browser/plugin prefetches it. | Unauthorized deletion/disablement of tenant and configuration records, causing integrity loss and service disruption. | **Planned for Stage 10:** use `DELETE`/`POST`, require CSRF protection and authorization, show confirmation, and record an audit event. |
| Admin bill-format uploads — **Medium** | Uploaded files are stored under the public web root using predictable timestamps plus the original client filename. Existing files are not safely replaced or cleaned up. Evidence: `admin/BillFormats.php:86–108,278–299`. | Authenticated attackers use crafted filenames, collide with another upload in the same second, upload active PDF content, or create many orphaned public files. | Two uploads named `invoice.pdf` in the same second can target the same public filename; uploaded PDFs are served from the application origin. | Possible overwrite, stored-content delivery, phishing from a trusted origin, storage exhaustion, and disclosure of uploaded templates. No breach is confirmed. | **Partially resolved:** migrated profile logos use generated UUID names, strict size/MIME/signature checks, controlled paths, and failure cleanup. Stage 10 must apply equivalent handling to bill-format files, store them outside executable paths, and serve with safe content headers. |
| Debug and error configuration — **Medium** | The legacy example environment enables `APP_DEBUG=true` and `LOG_LEVEL=debug`. Some controllers return raw exception messages in UI errors. Evidence: `dev/.env.example:4,21` and `admin/Clients.php` catch blocks such as `with('error', $e->getMessage())`. | If copied into an exposed environment, an attacker deliberately triggers failures to obtain stack traces, SQL/database details, paths, or configuration context. | Submit malformed contract/profile data until a database exception is rendered or logged. | Potential disclosure of internal paths, SQL/schema details, dependency versions, and occasionally secrets embedded in errors. No breach is confirmed. | **Resolved for the Node foundation:** client responses are generic and readiness checks do not expose database errors. Production configuration and deployment checks must keep debug output disabled. |
| Bill-format selection — **Medium** | The legacy client endpoint accepts any integer and writes it to `billing_settings`; it does not verify that the format exists, is active, or belongs to the client's business type. Evidence: `Api/Login.php`, `updateBillFormat`, around lines 1180–1270. | An authenticated tenant user selects nonexistent, deleted, or another business type's format ID and corrupts billing configuration. | `POST /api/updateBillFormat` with `{"id":999999}` succeeds if billing settings exist. | Integrity loss in invoice generation; possible cross-business template exposure depending on later rendering logic. No breach is confirmed. | **Resolved:** Node validates an active, non-deleted format for the authenticated client's business type, updates transactionally, and creates an audit record. |
| Audit report retrieval — **Medium** | Omitting `page` makes the legacy endpoint set page size to the total row count, allowing an unbounded audit query and response. Evidence: `Api/Login.php`, `getAuditReports`, around lines 1095–1100. | An authenticated user repeatedly requests the entire audit history for a large tenant, consuming database, memory, CPU, and network capacity. | `POST /api/getAuditReports` with `{}` returns every matching audit row. | Availability degradation and bulk exposure of audit descriptions to any compromised authorized account. No breach is confirmed. | **Resolved:** Node always paginates with a configurable limit of 1–100 rows, defaults to 25, validates filters, and enforces `client_id`. |

## Review notes

- Laravel query-builder calls using bound `where` values were not labeled SQL injection vulnerabilities. A few raw aggregate expressions use server-selected table names; these need replacement during billing conversion, but the reviewed source did not establish direct user-controlled SQL interpolation.
- `APP_DEBUG=true` is confirmed in the example configuration, not in a deployed production environment.
- “No breach is confirmed” means this repository review did not examine production logs, databases, access records, or incident telemetry.
- Dependency advisories for the new Prisma/MariaDB toolchain are tracked separately in `MIGRATION_TRACKER.md` and the backend `README.md`; this file focuses on weaknesses discovered in the old Laravel application.
